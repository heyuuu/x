# IsLower 各实现方式性能对比

对比 ASCII 字符判断的几种写法——区间比较、`[256]` 查表、位图——看 `IsLower` 这类函数
是否有必要用查表实现。结论先行：**区间比较不慢于任何查表**，包内判断函数统一维持
区间比较写法。

## 被对比的实现

| 实现 | 写法 | 来源 |
| --- | --- | --- |
| 区间比较 | `'a' <= c && c <= 'z'` | 本包 `IsLower` 的写法 |
| Bool 表 | `table[c]`，`[256]bool` | 布尔查表 |
| Kind 表 | `kind[c] == kindLower`，`[256]uint8` | 枚举查表，`xstrings.byteKinds` 风格 |
| 位图 | `bits[c>>3]&(1<<(c&7)) != 0`，`[32]byte` | `unicode` 标准库风格 |

benchmark 见 [bench_test.go](./bench_test.go)。

## 结果

Apple M1 Pro / Go 1.27.1，扫描 4096 字节/次，`-count=6` 取均值。绝对数值因机器而异，
量级关系稳定：

| 实现 | ns/字符 | 相对区间比较 |
| --- | --- | --- |
| 区间比较（非泛型） | ~0.45 | 1.00 |
| Kind 表 | ~0.48 | 1.07 |
| Bool 表 | ~0.48 | 1.08 |
| 区间比较（泛型 `IsLower`） | ~0.51 | 1.13 |
| 位图 | ~0.72 | 1.60 |

## 结论

1. **区间比较、Bool 表、Kind 表三者 ±10% 以内，基本等价**。每字符约 0.5 ns
   （吞吐 ~2 GB/s），瓶颈是循环本身而不是判断方式——查表省下的比较指令被一次
   L1 load 抵消了。
2. **位图慢约 60%**，不采用。`unicode` 标准库用位图是为了省内存（21 位 rune 的
   完整判定表太大），不是为了快；对 256 项的 ASCII 表纯属吃亏。
3. **输入分布对性能无影响**（全小写 / 全非小写 / 均匀随机三者差距 < 2%）：编译器
   把判断+计数生成无分支代码（arm64 上为 `SUB`+`CMP`+`CINC`），分支预测不构成
   选型考量。
4. **泛型 `IsLower[T byte | rune]` 比非泛型慢约 10%，属编译器产物而非本质开销**：
   反汇编确认两者内循环逐指令相同，仅泛型内联边界多一条编译器插入的 `NOP`，每迭代
   多占一个发射槽。折合每字符 0.05 ns，不构成弃用泛型的理由。
5. **因此本包判断函数统一用区间比较**：性能不劣于查表；天然支持 rune（查表按字节
   索引，传入 rune 需先做范围检查防越界 panic）；代码最直观。
